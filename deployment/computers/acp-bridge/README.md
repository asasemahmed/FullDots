# Coding worker policy and adapter verification

The bridge starts the coding agent named in the `x-fulldots-coding-provider` header: `claude` (the default when the header is missing) or `codex`. Any other name is refused with 400 before an upgrade, an install or a process. Each agent has its own version, lockfile folder, cache and completion marker in `PROVIDERS` in `bridge.mjs`, and the bridge says which agent it started in its ready message. Both share one private home, with `.claude` and `.codex` inside it.

The Claude Code adapter cache and home are `/profiles/.coding/adapters/claude-0.95.0` and `/profiles/.coding/home`. `/workspace` remains the project working directory. The computer's existing profiles volume makes the private paths persistent; the Files API is confined to the separate workspace root. `storage.mjs` checks the real cache, home, staging and executable paths before launch. A link into the workspace fails closed. Startup quarantines the earlier workspace sign-in home before the computer API begins accepting requests; it never promotes the earlier writable adapter or settings into the new runtime.

The image copies `managed-settings.json` to `/etc/claude-code/managed-settings.json`, owned by root with mode 0444. The bridge checks its ownership, permissions and exact shipped contents before launch. The policy locks permission rules and hooks to managed sources, disables bypass and auto modes, keeps default mode manual, and provides no pre-allowed actions. SDK hooks belonging to the pinned adapter remain available; project, user and plugin hooks cannot add permission decisions. The app also refuses mode-changing permission choices and cancels sessions reporting any non-default mode.

## What was verified for adapter 0.95.0

The published npm artifact was inspected directly, including `dist/acp-agent.js`, `dist/settings.js`, `dist/managed-policy.js` and the permission-option builders. Its locked runtime SDK is `@anthropic-ai/claude-agent-sdk@0.3.309`.

- `SettingsManager.loadAllSettings()` normally resolves settings for the project with all default sources, and watches user, project, local and managed files. Merely overriding the SDK query options does not restrict this separate manager. `harden-adapter.mjs` changes its one pinned resolution call to pass `settingSources: []`. A missing or ambiguous patch target rejects installation. The completion marker records the policy revision, so an unhardened cache is not reused.
- Query construction normally starts with `settingSources: ["user", "project", "local"]`, then applies `_meta.claudeCode.options`. The client supplies an empty list and `allowDangerouslySkipPermissions: false`. A strict MCP configuration flag prevents additional project/user MCP server configuration from starting processes. The adapter retains its own `canUseTool` callback and chooses the initial mode from the now managed-only settings.
- The SDK loads managed settings even when its regular setting sources are empty. This follows the [managed-settings contract](https://code.claude.com/docs/en/managed-settings#where-and-when-a-policy-applies). The policy's [permission rules](https://code.claude.com/docs/en/permissions) ask before shell commands and edits and deny native file-tool access to the private coding and managed-policy directories.
- A real Docker trial planted conflicting user/project allow rules, bypass defaults, a sign-in helper and a startup hook. The actual hardened `SettingsManager` resolved only the shipped managed rules and hooks. The real adapter initialized in default mode and reached the expected authentication-required response; neither planted command ran. The native dependency binaries still worked after an install with lifecycle scripts disabled. No authenticated model execution or real account was used, so this is settings-resolution and authentication-boundary evidence, not a claim to have exercised signed-in model-driven edits.
- The real Files API returned 403 for path traversal and symlink reads of the private credential file and writes of the private adapter entry. A WebSocket frame over 1 MiB was rejected by Bun's payload limit before the bridge message handler. Unit tests additionally cover real-path aliases, permission options, mode changes, buffering and concurrency errors.

Managed settings constrain the worker; they are not an OS isolation boundary against an owner-approved command running with the computer's privileges. Do not restore the quarantined home as active settings. Sign in again with the protected home configured as shown in [the computer guide](../../../docs/COMPUTERS.md#coding-agents).

## What was verified for Codex adapter 2.2.2

The published npm artifact `@agentclientprotocol/codex-acp@2.2.2` (Apache-2.0) was read directly. Its entry is `dist/index.js`, which is also its `main` and `bin`. It starts the bundled `@openai/codex` app server and keeps its state in `CODEX_HOME`.

- Modes (`AgentMode` in `dist/index.js`): `read-only`, `workspace-write`, `agent` (the default, "Auto review") and `agent-full-access` (never asks). Only `read-only` has a read-only sandbox with owner approval for edits. The start preset comes from the `INITIAL_AGENT_MODE` variable, so the bridge sets it to `read-only`, and the app selects and checks the mode again. Modes are not reported before sign-in; `session/new` fails with `-32000 Authentication required` first.
- The adapter marks the session folder as a trusted Codex project, which would load a project `.codex` configuration from the writable Files root. `untrustedProjectCodexSettings` in `harden-adapter.mjs` replaces that single token with `untrusted`, and refuses to install if the token is missing or repeated. This relies on Codex ignoring the configuration of an untrusted project. It was not exercised against a signed-in session.
- Permission requests offer `allow_once` and `allow_always` options. Options that grant for a session, change preset or implement a plan are refused by the app.
- Not verified: authenticated model runs, the Linux sandbox inside a container, and Read-only's file reads. The preset does not restrict reads, so Codex can read the private sign-in file. Managed settings above apply to Claude Code only.
